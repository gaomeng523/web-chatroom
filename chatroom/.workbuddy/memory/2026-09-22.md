## 发现的关键风险 / 待决策点

1. **鉴权路线与课件分叉**：课件用 HttpSession + `req.getSession(false).getAttribute("user")`；本项目用 JWT + localStorage。后续所有接口都要改为从 token 解析当前用户。
2. **WebSocket 鉴权是最大坑**：浏览器原生 WebSocket 构造器不能自定义请求头，JWT 无法像 HttpSession 那样靠 Cookie 自动携带。可选方案：token 放 URL query 用 HandshakeInterceptor 解析；或用 Sec-WebSocket-Protocol；或退回 Cookie/Session 方案。需提前决策。
3. **`/userInfo` 字段名不一致（真实 bug）**：`User` 实体字段是 `userName`，Jackson 序列化为 `userName`，而 client.js 读的是 `body.username` → 会得到 undefined。同时直接返回实体还会泄露 password。应新建 UserInfoResponse。
4. **MyBatis-Plus 与 XML 混用**：若要用 XML mapper，需显式配置 `mybatis-plus.mapper-locations`（注意是 mybatis-plus 前缀，非 mybatis）。
5. **静态页面无法服务端鉴权**：client.html 是静态资源，只能靠前端 JS 在 /userInfo 失败时跳回登录页（client.js 已实现）。

## 代码评审：用户自己写的拦截器（2026-09-22 23:00）

用户新增了 3 个文件：`common/interceptor/LoginInterceptor.java`、`common/interceptor/LogInterceptor.java`、`common/constant/Constant.java`、`config/WebConfig.java`。

审查发现的 4 个问题（按严重度）：

1. **P0 启动即失败**：`LogInterceptor` 没有 `@Component`，但 `WebConfig` 用构造器注入了它 → `NoSuchBeanDefinitionException`。
2. **P0 逻辑永远 401**：claim 名不一致。`UserServiceImpl:42` 写的是 `userId`，`Constant.JWT_CLAIM_ID = "id"`，拦截器读 `claims.get("id")` 恒为 null → 每个合法 token 都被判 401。
3. **P0 拦截路径是博客项目遗留**：`WebConfig` 里写的是 `/blog/addBlog`、`/blog/updateBlog`、`/blog/deleteBlog`、`/user/getUserInfo`（项目 artifactId 都还叫 spring-blog-demo）。应改为「拦 `/**` + 排除放行清单」的黑名单式，避免新增接口漏加导致静默无鉴权。同时必须排除 `/error`，否则异常转发到 /error 会被再拦一次、401 覆盖真实错误。
4. **P0 前端没带请求头**：全项目 grep `User-Token` 只有后端拦截器一处。login.html 只把 token 存进 localStorage，client.js 的 ajax 没有设置请求头 → 后端永远收不到 token。需在 client.js 顶部加 `$.ajaxSetup({ headers: { 'User-Token': localStorage.getItem('token') || '' } })`。

其他建议（P1/P2）：`preHandle` 补 `@Override`（防手抖写成重载导致静默失效）；401 补 JSON 响应体；除 userId 外把 username 也放进 request attribute（后面 /userInfo、WebSocket 转发都要用）。

**关键事实**：`spring-blog.log` 最后写入时间 22:15，而拦截器文件创建于 22:55~23:00 → 这套代码从未真正启动运行过，所有问题都还没暴露。
